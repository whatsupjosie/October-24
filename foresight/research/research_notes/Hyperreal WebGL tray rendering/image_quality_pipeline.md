# Image-quality pipeline for a "hyper-real" WebGL2 UI on integrated laptop GPUs (Foresight Counter)

Research date: 2026-10-13. Scope: browser-only, WebGL2 primary, WebGPU where it changes the answer. Context: full-screen WebGL2 canvas behind HTML; bench + trays drawn as premultiplied-alpha quads; today per-fragment ACES fit + gamma 2.2, 8-bit default framebuffer, 2x-DPR supersampling, analytic halos for glow.

Note on method: several primary sources (Jimenez slides PDF, LearnOpenGL physically-based bloom article, Khronos PBR Neutral README, Bjorge dual-Kawase talk) could not be fetched in this session; where details come from prior knowledge rather than a fetched page they are placed under Inferences and marked "not re-verified this session".

## 1. HDR rendering in WebGL2: float render targets, linear workflow, sRGB/P3 output, and per-fragment tone mapping with alpha blending

### Takeaway
Float render targets are effectively universal on WebGL2 in 2026 (EXT_color_buffer_float on ~99.95% of tested WebGL2 browsers), so the correct architecture is: composite all trays in linear HDR into an RGBA16F (or R11F_G11F_B10F) offscreen target, then tone map once in a final full-screen pass. Tone mapping per fragment before premultiplied blending is mathematically wrong (blending a non-linear, display-referred signal) and is a likely contributor to the flat, "pixelated" look.

### Cited Findings
- EXT_color_buffer_float is supported by 99.95% of WebGL2 browsers tested by Web3DSurvey; by OS: Windows 99.98%, macOS 99.97%, ChromeOS 100%, iOS 100%, Android 99.91%, Linux 99.53%; by browser: Edge 100%, Safari 100%, Firefox 99.99%, Chrome/Chromium 99.93%. The page states no sample date/period. — [Web3DSurvey: EXT_color_buffer_float](https://web3dsurvey.com/webgl2/extensions/EXT_color_buffer_float)
- With EXT_color_buffer_float enabled, R16F, RG16F, RGBA16F, R32F, RG32F, RGBA32F and R11F_G11F_B10F become color-renderable (RGB16F is excluded); "Fragment shader outputs to buffers with these internal formats are not clamped"; "Multi-sample floating-point color renderbuffers may optionally be supported." — [Khronos WebGL registry: EXT_color_buffer_float](https://registry.khronos.org/webgl/extensions/EXT_color_buffer_float/)
- A separate EXT_float_blend extension exists for WebGL2 (tracked by Web3DSurvey). — [Web3DSurvey: EXT_float_blend](https://web3dsurvey.com/webgl2/extensions/EXT_float_blend)
- Chromium implements `gl.drawingBufferStorage(gl.RGBA16F, w, h)` to make the WebGL canvas drawing buffer itself floating-point; Chromium's pixel test gates it on `EXT_color_buffer_half_float` and creates the context with `{premultipliedAlpha: true, antialias: false}`. — [Chromium pixel_webgl_float.html test](https://chromium.googlesource.com/chromium/src/+/main/content/test/data/gpu/pixel_webgl_float.html)
- HDR output for WebGL (a `drawingBufferToneMapping` method, paired in discussion with RGBA16F storage and a `"rec2100-linear"` color space) is still an open, unmerged proposal; Chromium's ccameron blocked the HDR10 mode pending `rec2100-pq` work. The thread also notes "Resolving in non-linear spaces (such as RGBA16F with "srgb") gives incorrect results. Linear color spaces are recommended." — [KhronosGroup/WebGL PR #3668](https://github.com/KhronosGroup/WebGL/pull/3668)
- `drawingBufferColorSpace` accepts `"srgb"` (default) and `"display-p3"`; MDN marks it Baseline 2024 ("Newly available" across latest browsers since October 2024) and usable in workers; texture upload color space is set separately via `unpackColorSpace`. — [MDN: drawingBufferColorSpace](https://developer.mozilla.org/en-US/docs/Web/API/WebGLRenderingContext/drawingBufferColorSpace)
- pmndrs/postprocessing (the de-facto three.js post stack) defaults to `UnsignedByteType` sRGB frame buffers, but says `HalfFloatType` buffers (linear, high precision) are "the preferred option for HDR-like workflows on desktop devices"; it requires the renderer's own `toneMapping` to stay at `NoToneMapping` and tone mapping to be done by "a `ToneMappingEffect` at the end of the pipeline." — [pmndrs/postprocessing README](https://github.com/pmndrs/postprocessing)

### Inferences
- Why per-fragment tone mapping + premultiplied blending is wrong: blending computes `dst = src + (1 - a_src) * dst`. If `src` and `dst` are already tone-mapped and gamma-encoded, the result is `T(x)` blended with `T(y)`, not `T(blend(x, y))`. Consequences visible in this UI: (a) glass/translucent tray edges and AA ramps get dark or muddy fringes because coverage is mixed in a gamma-encoded space; (b) overlapping glows/halos clip at 1.0 per-object instead of adding energy, so highlights look flat and "sticker-like" instead of luminous; (c) no >1.0 values survive, so no physically-based bloom can be derived later; (d) the ACES curve's contrast/saturation is applied per layer, compounding shifts where layers overlap. (Mathematical consequence of the blend equation; no single source fetched.)
- Nuance: browsers composite HTML/CSS in gamma-encoded sRGB, so UI-native pieces that must visually match CSS (thin strokes, text-like hairlines) may intentionally be blended in sRGB space. For the physical materials (metal, glass, stone, wood), linear-space blending is the right model; the PR #3668 note that non-linear resolves are "incorrect" supports doing coverage/resolve math in linear.
- Format choice: R11F_G11F_B10F is 4 bytes/pixel (same bandwidth as RGBA8) vs 8 bytes/pixel for RGBA16F, and premultiplied OVER (`ONE, ONE_MINUS_SRC_ALPHA`) only reads source alpha from the fragment output, so an opaque-background HDR scene target does not need a stored alpha channel. That makes R11F_G11F_B10F the bandwidth-optimal HDR scene and bloom-mip format on integrated GPUs; use RGBA16F only where destination alpha must be kept (e.g., a cached transparent layer). Caveat: R11G11B10F has no sign bit and ~5-6 bits of mantissa, so it is fine for color/bloom but not for signed or precise data. (Format sizes are arithmetic from the format definitions; blending support on 16F/11-11-10F under EXT_color_buffer_float without EXT_float_blend is from prior knowledge of the GLES 3.2/WebGL rules, not re-verified this session — test `gl.checkFramebufferStatus` plus a blend readback at startup.)
- Replace the "gamma 2.2" encode with the exact piecewise sRGB OETF (or render the final pass into an `SRGB8_ALPHA8` texture and blit), because the canvas is interpreted as sRGB; pure 2.2 crushes the darkest values relative to sRGB, which is exactly where dark-gradient banding shows. (Prior knowledge; not re-verified this session.)
- If switching the canvas to `drawingBufferColorSpace = "display-p3"`, the final pass must convert linear-sRGB-primaried values to P3 primaries (3x3 matrix) before encoding, otherwise every color is silently oversaturated. Khronos PBR Neutral is specified for sRGB output only (see section 2), so on P3 either tone map in sRGB then matrix-convert, or accept an un-specified wider-gamut look.
- Opaque canvas: since the canvas sits behind HTML and covers the screen, creating the context with `alpha: false` lets the compositor skip blending the canvas with the page and avoids premultiplied-alpha surprises at the final output. (Prior knowledge of context attributes; not re-verified this session.)

#### Recommended pipeline order (synthesis across all sections)
1. Static cache: render the bench (and any tray not being dragged) once into a linear HDR texture at native device pixels; re-render only on resize, theme change, or when its content changes.
2. Scene pass (linear HDR, R11F_G11F_B10F or RGBA16F FBO, 1x native device pixels, not 2x): blit/sample the cached bench, then draw trays with premultiplied-alpha OVER in linear light. Shape edges use analytic SDF coverage via `fwidth` (section 4). Specular highlights and emissive accents are allowed to exceed 1.0; delete the analytic halos and let bloom produce glow, or keep halos only as linear HDR emissive (not post-tone-map additive).
3. Bloom (section 3): downsample chain from the scene target into 5-6 half-res-and-smaller R11F_G11F_B10F mips (13-tap filter, 1/(1+luma) weighting on the first downsample), then 3x3 tent upsample with additive accumulation; no threshold.
4. Single final "uber" pass to the default framebuffer: `scene = mix(scene, bloom, ~0.04)` → exposure → tone map (Khronos PBR Neutral or AgX, section 2) → optional 3D-LUT grade → subtle vignette → (optional) P3 matrix → exact sRGB OETF → triangular-PDF or blue-noise dither of ±1 LSB (section 5) → write RGBA8.
5. Optional last: CAS sharpening only when rendering below native (dynamic resolution while dragging); per AMD, CAS expects linear input, so either run it inside the final pass before the OETF or tell it the color space (section 6).
6. HTML text stays in the DOM above the canvas and is untouched by any of this.

## 2. Tone mapping choices in 2026 (ACES Narkowicz/Hill, AgX, Khronos PBR Neutral, Tony McMapface, Gran Turismo/Uchimura) for jewel tones, gold and white marble

### Takeaway
For a UI whose value is accurate, saturated material color (jewel tones, gold, white marble), the best default is Khronos PBR Neutral: it reproduces base color 1:1 up to a knee and only compresses highlights, with no imposed look, in ~13 lines of GLSL. AgX is the best "filmic" alternative (neutral, little hue shift, but deliberately low-contrast/desaturated, so it needs a grade on top). The current ACES fit is the worst fit for this brief: it shifts hues (reds/greens toward orange, blues toward magenta, oranges toward yellow) and darkens/adds contrast.

### Cited Findings
- Khronos PBR Neutral (released May 16, 2024) aims for "faithful reproduction of a product's base color, hue and saturation when using PBR rendering under grayscale lighting," a 1:1 match up to a maximum value with the rest used as highlight headroom, "un-opinionated representation under colored light," and removal of "HDR artifacts around highlights"; it is "simple to implement and fast to run" (13-line GLSL sample), analytically invertible, and currently outputs only to sRGB. — [GameDev.net: Khronos PBR Neutral released](https://gamedev.net/news/khronos-pbr-neutral-tone-mapper-released-for-true-to-life-color-rendering-of-3d-objects-r2733); [Khronos news](https://www.khronos.org/news/permalink/khronos-pbr-neutral-tone-mapper-released-for-true-to-life-color-rendering-of-3d-products)
- The same announcement says ACES has a "limited range of reachable colors," especially bright yellow, green and cyan on sRGB displays, which can make objects look washed out; filmic mappers (ACES, AgX) suit "strongly HDR scenes," wide-gamut input, or specific artistic looks. — [GameDev.net](https://gamedev.net/news/khronos-pbr-neutral-tone-mapper-released-for-true-to-life-color-rendering-of-3d-objects-r2733)
- Adopters of PBR Neutral named by Khronos: model-viewer, Autodesk, Babylon.js, Blender (4.2), Dassault, Filament, London Dynamics, Phasmatic, three.js, Threekit; spec at github.com/KhronosGroup/ToneMapping/blob/main/PBR_Neutral/README.md. — [GameDev.net](https://gamedev.net/news/khronos-pbr-neutral-tone-mapper-released-for-true-to-life-color-rendering-of-3d-objects-r2733); Blender integration PR: [projects.blender.org #118936](https://projects.blender.org/blender/blender/pulls/118936); PlayCanvas exposes it as `TONEMAP_NEUTRAL`: [PlayCanvas API](https://api.playcanvas.com/engine/variables/TONEMAP_NEUTRAL.html)
- Bevy's documented characterization of tone mappers: AcesFitted (the Godot 4 ACES fit) "is not neutral" with a strong look: bright greens and reds shift toward orange, bright blues toward magenta, contrast increases significantly, brights desaturate. AgX (Troy Sobotka) is "very neutral," somewhat desaturated, with little to no hue shifting and subtle Abney shifting, and needs a LUT. TonyMcMapface (Tomasz Stachowiak; Bevy's default) is very neutral with subtle intentional hue shifting, brights desaturate, intentionally adds no contrast or saturation, and needs a LUT. BlenderFilmic suffers from hue shifting. Reinhard has heavy hue shifting and bright primaries do not desaturate at all. — [Bevy Tonemapping enum docs](https://doc.qu1x.dev/bevy_trackball/bevy/core_pipeline/tonemapping/enum.Tonemapping.html)
- three.js community comparison: "ACES changes your colors, not just the intensities" (oranges drift to yellow, water to cyan); ACES "boosts contrast and tends to darken your image"; AgX is flatter by design; Khronos PBR Neutral is "a solid choice" for accurate product color (one user found it "a bit over saturated" in their scene). Don McCurdy: tone mapping is "picture formation"; original ACES was "designed for a darkened theatre"; AgX "very intentionally aims at a low-contrast default look," good as a base for grading; stylistic choices "should ideally be controlled separately by a color grading API." Tone mapping cost is "practically free." — [three.js forum: Tone Mapping Overview](https://discourse.threejs.org/t/tone-mapping-overview/75204)
- A three.js forum thread questions whether three.js's AgX implementation is correct, i.e., AgX ports vary. — [three.js forum: Is AgX implemented correctly?](https://discourse.threejs.org/t/is-agx-tonemapping-implemented-correctly/60609)
- A Unity port of Tony McMapface exists (it is LUT-based). — [unitycoder/tony-mcmapface-tonemapping-unity](https://github.com/unitycoder/tony-mcmapface-tonemapping-unity)

### Inferences
- Gold: gold's base color is a saturated yellow-orange; ACES pushes oranges toward yellow and clips bright yellows ("limited range of reachable colors" for yellow), so specular gold highlights go lemon/flat. PBR Neutral keeps the base hue and compresses only above the knee; AgX keeps hue but desaturates highlights toward white, which reads as "hot metal sheen" (often desirable for gold sparkle).
- White marble: needs neutral whites without the ACES darkening; both PBR Neutral and AgX keep near-white neutral. PBR Neutral also preserves faint veining color better because it is 1:1 below the knee.
- Jewel tones (emerald, sapphire, ruby): ACES moves bright greens/reds toward orange and blues toward magenta; avoid. PBR Neutral keeps them; AgX keeps hue but pulls saturation down, so it pairs with a small saturation/contrast grade (3D LUT) to look "elevated."
- Practical recommendation: ship Khronos PBR Neutral as the default (no LUT download, ~13 ALU lines), optionally expose AgX + a tiny LUT grade as a "cinematic" mode. Tony McMapface requires a 3D LUT texture (small, but an extra asset) and has subtle intentional hue shifts; it offers little over Neutral for a product-accuracy brief.
- Not re-verified this session (prior knowledge): the Narkowicz 2016 ACES fit is a 5-coefficient rational curve applied per channel (hence its hue shifts and over-saturation in brights); Stephen Hill's fit (BakingLab) applies the ACES RRT+ODT input/output matrices around a rational fit and is closer to reference ACES; Uchimura's Gran Turismo curve is a per-channel piecewise curve with a linear mid-section, so it preserves mid-tone color well but, being per-channel, still skews hues in bright saturated regions.

- No fetched side-by-side images or measurements of the five mappers on gold/marble/jewel-tone swatches; the per-material verdicts are inferences from documented hue-shift behavior.
- Gran Turismo/Uchimura and ACES Hill-fit characterizations not sourced this session.

## 3. Physically-based bloom (Jimenez 2014 downsample/upsample chain, dual Kawase, energy conservation, threshold vs none) and its cost

### Takeaway
Use the Call of Duty: Advanced Warfare scheme: a mip pyramid built with a wide downsample filter (firefly-suppressed on the first step), blurred back up with a 3x3 tent and accumulated, then mixed in at a small constant (about 0.04) with no threshold. This replaces the analytic halos, needs an HDR scene buffer, and costs roughly one third of a full-screen pass's pixels per direction, which fits integrated GPUs at 1440p.

### Cited Findings
- Jimenez, "Next Generation Post Processing in Call of Duty: Advanced Warfare," SIGGRAPH 2014 Advances in Real-Time Rendering course (slides posted Aug 28, 2014): bloom uses "a pyramidal filter hierarchy that improves temporal stability and robustness." — [iryoku.com](https://www.iryoku.com/?p=1707)
- No threshold: "When using PBR the dynamic range is usually very high, so you don't need to threshold. The blurred bloom layer is set to a low value (say 0.04), which means that only very bright pixels will bloom noticeably." — [iryoku.com](https://www.iryoku.com/?p=1707)
- Firefly suppression: when downsampling mip0 to mip1, weight samples by 1/(1+luma) "on each 2x2 block" and renormalize ("it's a weighted average"). — [iryoku.com](https://www.iryoku.com/?p=1707)
- Upsampling uses a 3x3 tent filter; "We use a custom per-mip radius for the tent filter," by default the same UV-space radius per level; "You need a few iterations to converge to a Gaussian"; filtering is done on the fly for both downsample and upsample. Mips up to 6 are referenced. — [iryoku.com](https://www.iryoku.com/?p=1707)
- The page's only timing figure is the frame budget ("16.6 ms for a 60 fps game"); no per-effect ms numbers are given there. — [iryoku.com](https://www.iryoku.com/?p=1707)
- A widely used open implementation of this style of bloom chain exists for MonoGame/XNA. — [Kosmonaut3d BloomFilter](https://github.com/Kosmonaut3d/BloomFilter-for-Monogame-and-XNA)
- Dual Kawase blur is adopted for cheap large-radius blurs in production desktop compositors and apps (KDE KWin blur effect, VLC Qt UI, GNOME/GTK discussion, Godot shaders). — [KWin blur.h](https://invent.kde.org/plasma/kwin/-/blob/0179f741bbd4cc01da5866fdf7b6a302869a099b/effects/blur/blur.h); [VLC MR "qt: use Dual Kawase blur"](https://code.videolan.org/videolan/vlc/-/merge_requests/7461); [GTK blur issue](https://gitlab.gnome.org/GNOME/gtk/issues/1283); [Godot Dual Kawase shader](https://godotshaders.com/shader/dual-kawase-up-fast-blur/)
- pmndrs/postprocessing ships a Bloom effect and merges effects into a single EffectPass to avoid pass-chaining cost, using a single full-screen triangle. — [pmndrs/postprocessing](https://github.com/pmndrs/postprocessing)

### Inferences
- Not re-verified this session (prior knowledge of the slides/LearnOpenGL article): the downsample is a 13-tap filter formed from five overlapping 4-tap boxes (center box weight 0.5, four corner boxes 0.125 each), which kills the pulsing/aliasing of naive 2x2 box downsamples; the 1/(1+luma) weighting is commonly called a "Karis average" after Brian Karis. The Jimenez page itself did not name the 13-tap pattern.
- Energy conservation: mixing `lerp(scene, bloom, 0.04)` (rather than `scene + k*bloom`) keeps total energy constant, so bloom never brightens the frame overall; only pixels that are much brighter than their surroundings visibly glow. For this UI that means: author specular glints and emissive accents at 4-20x the diffuse level so they bloom, and keep the bench/tray diffuse under ~1.0 so they stay crisp. No threshold also means no "threshold pop" when a tray is dragged.
- Dual Kawase vs Jimenez: dual Kawase (prior knowledge, not re-verified: Marius Bjorge, ARM, SIGGRAPH 2015 "Bandwidth-Efficient Rendering"; 5-tap downsample, 8-tap upsample with half-pixel offsets) is cheaper per pixel and excellent for frosted-glass background blur, but it is a blur, not a bloom model: it lacks the firefly suppression and the per-mip energy weighting. Use Jimenez for bloom; use dual Kawase for the glass trays' "frosted" see-through blur if needed (it can reuse the same mip chain).
- Cost arithmetic at 1440p (2560x1440 = 3.69 MP): the mip chain from half-res down holds 1/4 + 1/16 + 1/64 + ... ≈ 1/3 of the full-res pixel count. One downsample sweep plus one upsample sweep writes ≈ 0.67 full-screen-equivalents; in R11F_G11F_B10F (4 B/px) that is ≈ 10 MB of writes plus texture reads that are mostly cache hits. At 60 fps this is under 1 GB/s of writes, small next to the scene pass. Measured ms on Iris Xe is a gap (see Gaps).
- Start the chain at half resolution (the first downsample reads full-res scene), never compute bloom at full res; that is the single biggest cost lever.

## 4. Anti-aliasing for SDF-drawn UI: analytic fwidth AA, supersampling vs MSAA, FXAA/SMAA/TAA, specular aliasing

### Takeaway
For SDF-drawn rounded polygons, analytic coverage (signed distance divided by its screen-space derivative, ramped over ~1-1.25 output pixels) gives the cleanest edges at 1x native resolution and is far cheaper than 2x supersampling (which costs 4x the pixels). Add MSAA only for true triangle edges, add FXAA/SMAA only if specular/texture aliasing remains, and avoid TAA for a mostly static UI.

### Cited Findings
- SDF edge AA should scale with output pixels, not input distance: with `screenPxRange` = output pixels per distance unit, the ramp width in distance units is `edge_blur_px / screenPxRange`; the author found ~0.5 px looks blocky and ~2.0 px blurry, and settled on 1.2 px (1.25-1.3 possibly better for large shapes); results differ by browser/OS (Chrome on Mac renders differently). — [Red Blob Games: SDF antialiasing (2024)](https://redblobgames.com/blog/2024-09-22-sdf-antialiasing)
- pmndrs/postprocessing recommends creating the renderer with `antialias: false` (doing AA as a post effect), and its ecosystem ships SMAA and FXAA effects. — [pmndrs/postprocessing](https://github.com/pmndrs/postprocessing); [react-postprocessing SMAA](https://react-postprocessing.docs.pmnd.rs/effects/smaa); [react-postprocessing FXAA](https://react-postprocessing.docs.pmnd.rs/effects/fxaa)
- Multisampled floating-point color renderbuffers are optional under EXT_color_buffer_float. — [Khronos registry: EXT_color_buffer_float](https://registry.khronos.org/webgl/extensions/EXT_color_buffer_float/)
- The WebGL PR discussion states tone mapping happens after multisample resolve and that resolving in non-linear spaces is incorrect. — [KhronosGroup/WebGL PR #3668](https://github.com/KhronosGroup/WebGL/pull/3668)

### Inferences
- Recommended edge formula (prior knowledge, standard practice; not re-verified this session): `float d = sdf(p); float w = fwidth(d) * 0.6;` (≈1.2 px total ramp) `float coverage = clamp(0.5 - d / max(w * 2.0, 1e-5), 0.0, 1.0);` or `1.0 - smoothstep(-w, w, d)`. Multiply coverage into premultiplied output (`color.rgb *= coverage; color.a *= coverage`) in linear space. Use `length(vec2(dFdx(d), dFdy(d)))` instead of `fwidth` for rotation-invariant width when trays rotate. Compute the derivative on the distance before any non-linear remap and outside divergent branches.
- Why the current output looks "pixelated" despite 2x supersampling: if edges use `step()` or a fixed-width ramp, supersampling only gives 4 coverage levels (2x2), and the browser's compositor downscales the 2x canvas with bilinear filtering, which is not a proper box/tent resolve; combined with 8-bit quantization of tone-mapped gradients, edges stair-step and gradients band. Analytic coverage gives ~256 levels per edge at 1x.
- MSAA in WebGL2 (prior knowledge, not re-verified this session): create a renderbuffer with `renderbufferStorageMultisample(RENDERBUFFER, samples, RGBA8 | RGBA16F | R11F_G11F_B10F, w, h)`, render, then `blitFramebuffer` to a single-sample texture to resolve; query `getInternalformatParameter(RENDERBUFFER, format, SAMPLES)` for supported counts per format. MSAA only anti-aliases triangle edges, not SDF edges inside a quad, so for quad-drawn SDF trays it adds bandwidth with no benefit. The default framebuffer `antialias: true` only helps the final pass, which is a full-screen triangle, i.e., nothing.
- Resolve order: MSAA resolve (if any) in linear HDR, then bloom/tone map. Resolving after tone mapping is the "correct-looking edges" trick for very bright edges, but it is unnecessary when SDF coverage is analytic.
- Specular aliasing: thin, very bright highlights on brushed metal/gold frames (normal maps or procedural bump in the SDF bevel) will shimmer while dragging. Fix at the source: widen roughness by the normal's screen-space variance (Toksvig / Kaplanyan-style "specular AA" using `dFdx/dFdy` of the normal), and clamp specular peak before bloom. (Prior knowledge; no source fetched this session.)
- FXAA/SMAA: run on the tone-mapped LDR image (they are tuned for perceptual luma). They soften fine UI detail; use only if texture/specular aliasing remains after the above. SMAA needs two small lookup textures (area/search) that are an extra download (tens of KB); FXAA needs none. TAA requires motion vectors, jitter and history buffers, ghosts on moving UI, and blurs static text-like detail; not a fit here.
- Supersampling: keep it as a quality toggle for screenshots/stills only (render at 2x into an HDR FBO and do an explicit box or tent downsample in shader); do not rely on the compositor downscale.

## 5. Banding and dithering; display-P3 and HDR canvas status in 2026

### Takeaway
Add a ±1 LSB triangular-PDF (or blue-noise) dither in the final pass immediately before the 8-bit write; it removes banding in dark gradients and glow falloffs at essentially zero cost. Display-P3 WebGL output is broadly available (Baseline 2024). True HDR (above-white) canvas output exists only on WebGPU in Chromium (since Chrome 129); WebGL HDR output is still an unmerged proposal.

### Cited Findings
- Bart Wronski: white-noise dither clumps and leaves visible bands; doubling amplitude removes bands but is "too noisy"; triangular-PDF noise is "a much better solution" that fixes bands "without over-noising the image" (remapped to the -1..1 range); blue noise is "really great noise distribution for many dithering tasks" if you can afford to generate/store/fetch it, with no visible clumping and better behavior under blur/temporal use; Bayer gives visible unpleasant patterns; interleaved gradient noise is cheap and pleasant but can still pattern/alias. A commenter notes triangular dither lightens blacks and darkens whites because clipping breaks cancellation, suggesting adjusting values beyond black/white. — [Bart Wronski: Dithering part three](https://bartwronski.com/2016/10/30/dithering-part-three-real-world-2d-quantization-dithering/); series index: [Dithering in games mini-series](https://bartwronski.com/2016/10/30/dithering-in-games-mini-series/)
- Don McCurdy (three.js): dithering, grading and color management handle banding in most cases; three.js WebGPURenderer can output 16 bits per channel as of r173. — [three.js forum: Tone Mapping Overview](https://discourse.threejs.org/t/tone-mapping-overview/75204)
- `drawingBufferColorSpace` supports `"display-p3"`; Baseline 2024. — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebGLRenderingContext/drawingBufferColorSpace)
- Chrome 129 added HDR WebGPU canvases: `context.configure({ ..., format: "rgba16float", toneMapping: { mode: "extended" } })`; `"standard"` (default) clamps to SDR [0,1], `"extended"` unlocks the display's HDR range while matching standard within [0,1]. Chrome's WebGPU notes also list `srgb-linear` and `display-p3-linear` color spaces (Chrome 155-156) and display-p3 as a GPUExternalTexture color space (Chrome 121). — [Chrome: What's New in WebGPU 129](https://developer.chrome.com/blog/new-in-webgpu-129)
- WebGL HDR output (`drawingBufferToneMapping`) remains an open proposal; the WebGPU equivalent has "merged and shipped." — [KhronosGroup/WebGL PR #3668](https://github.com/KhronosGroup/WebGL/pull/3668)
- Chromium supports a float WebGL drawing buffer via `drawingBufferStorage(gl.RGBA16F, ...)`. — [Chromium pixel test](https://chromium.googlesource.com/chromium/src/+/main/content/test/data/gpu/pixel_webgl_float.html)

### Inferences
- Implementation (standard practice; not re-verified this session): after OETF encoding, `rgb += (tpdf(n1, n2)) / 255.0` where `tpdf = rand1 + rand2 - 1` (range -1..1 LSB). Use a hashed screen-space pixel coordinate (e.g., integer hash) for zero downloads; a 64x64 blue-noise texture is ~4-16 KB if a blue-noise look is wanted. Dither must happen after tone mapping and encoding, right before the 8-bit store; dithering earlier (in HDR) gets quantized away. Animate the noise per frame only if rendering continuously; with render-on-demand, keep it static to avoid shimmer between redraws.
- Apply the Wronski commenter's fix: fade dither amplitude to zero as the encoded value approaches 0 or 1, so pure blacks stay black and the bench's darkest corners do not look grey.
- The HDR scene buffer itself removes intermediate banding (glows computed in 8-bit gamma space band badly); dithering removes the final-quantization banding. Both are needed.
- Display-P3 is worth enabling only if materials are authored with wide-gamut colors (e.g., saturated emerald/sapphire beyond sRGB); otherwise it adds a conversion step for no visible gain on sRGB-gamut laptop panels. Many integrated-GPU Windows laptops have sRGB-class panels.
- HDR canvas (WebGPU extended tone mapping) would let gold glints and bloom cores exceed SDR white on HDR laptop panels, which is the most literal "elevated reality" upgrade, but it is Chromium-only and display-dependent; treat it as an optional enhancement path.

### Gaps
- Firefox and Safari support for WebGPU `toneMapping: { mode: "extended" }` was not confirmed.
- No source found for the fraction of integrated-GPU laptops with P3 or HDR panels.
- Per-browser support for WebGL `drawingBufferStorage` beyond Chromium was not found.

## 6. Cinematic finishing for "elevated reality" without looking cheap: vignette, chromatic aberration, grain, 3D-LUT grading, clarity, CAS sharpening

### Takeaway
Grading and a very subtle vignette help most; a 3D LUT on top of a neutral tone mapper is the professional way to add "look" without hue damage. Film grain only at near-invisible amplitude (doubling as dither). Chromatic aberration and strong clarity/sharpening are the effects most likely to read as cheap and to degrade the crispness of UI edges; CAS is only justified when rendering below native resolution.

### Cited Findings
- pmndrs/postprocessing ships Vignette, Chromatic Aberration and Noise (under Glitch), Color Grading including LUT, Brightness/Contrast, Hue/Saturation, and Tone Mapping, all mergeable into one EffectPass. — [pmndrs/postprocessing](https://github.com/pmndrs/postprocessing)
- Don McCurdy: AgX "very intentionally aims at a low-contrast default look" as a base for grading, and stylistic choices "should ideally be controlled separately by a color grading API." — [three.js forum](https://discourse.threejs.org/t/tone-mapping-overview/75204)
- AMD FidelityFX CAS (by Timothy Lottes, creator of FXAA) is a "low overhead adaptive sharpening algorithm with optional up-sampling," "created to provide natural sharpness without artifacts"; it expects linear input (or a declared color-space conversion), has a single sharpness parameter, and modes for sharpen-only or sharpen+upsample. — [FidelityFX SDK: Contrast Adaptive Sharpening](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/main/docs/techniques/contrast-adaptive-sharpening.md); standalone repo [GPUOpen-Effects/FidelityFX-CAS](https://github.com/GPUOpen-Effects/FidelityFX-CAS)

### Inferences
- Helps (keep): (1) a small 3D LUT grade (16^3 or 32^3 RGBA8 = 16-128 KB uncompressed, or generated procedurally at startup with zero download) for warmth in highlights and slight cool shadows, sampled as a `sampler3D` in the final pass with half-texel scale/offset; (2) vignette at 5-15% edge darkening with a wide smooth falloff, aspect-corrected, applied in linear before the tone map so it behaves like lens falloff; (3) bloom (section 3) as the main "weight/luminance" cue; (4) contact shadows / ambient occlusion under trays sitting on the bench (depth and weight), which can be analytic from the tray SDF (blurred SDF offset) at near-zero cost.
- Neutral to mildly helpful: film grain at amplitude ≈1-2 LSB, luminance-weighted (more in midtones, less in blacks/whites), static when rendering on demand. At that level it reads as "photographic" and doubles as the dither. Visible grain reads as "Instagram filter" and fights crisp UI.
- Hurts UI: chromatic aberration splits edges into colored fringes, which is exactly the "not crisp" look the user is trying to escape; if used at all, limit to <0.5 px at the screen corners only and never on interactive tray edges. Clarity/local contrast (unsharp mask on luminance at large radius) causes halos around high-contrast tray frames against the bench; if wanted, apply only to material textures (stone/wood detail) inside the material shader, not as a full-screen pass.
- CAS: at native resolution with analytic SDF AA, edges are already exact; sharpening adds ringing on the metal frame edges. Use CAS only with dynamic resolution (e.g., rendering at 0.67-0.75x while dragging) to restore apparent sharpness; port CAS's 3x3 min/max adaptive kernel to GLSL inside the final pass (prior knowledge of the CAS kernel; the fetched doc did not describe the kernel).
- Depth of field and motion blur: not recommended for a desktop UI; they blur interactive targets.

### Gaps
- No authoritative source was found that evaluates vignette/CA/grain/clarity specifically for UI legibility; recommendations are inferences from how each operator transforms edges.
- The fetched CAS doc did not give the kernel details or per-pixel cost; numbers are not sourced.

## 7. Performance strategy on integrated GPUs (render-on-demand, cached layers, dynamic resolution, half-res effects, GPU timing, 1080p/1440p budgets on Iris Xe)

### Takeaway
The biggest wins are structural: stop rendering at 2x DPR (4x pixels), render on demand instead of every frame, cache the bench in a texture, run bloom from half-res down, and merge all post into one final pass. GPU timing via EXT_disjoint_timer_query_webgl2 is available on most Chrome/Edge Windows installs but essentially absent in Firefox and Safari, so the app needs a CPU-side frame-time fallback.

### Cited Findings
- EXT_disjoint_timer_query_webgl2 is supported on 65.43% of tested browsers: Edge 94.19%, Chrome/Chromium 81.1%, Opera 87.71%, Safari 0.17%, Firefox 0.01%, Samsung Internet 0.65%; by OS: ChromeOS 99.34%, Windows 85.95%, macOS 59.85%, Linux 45.04%, Android 0.22%, iOS 0.16%. — [Web3DSurvey: EXT_disjoint_timer_query_webgl2](https://web3dsurvey.com/webgl2/extensions/EXT_disjoint_timer_query_webgl2); spec: [Khronos registry](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/)
- pmndrs/postprocessing performance guidance: merge effects with EffectPass to avoid pass-chaining cost, use a single full-screen triangle, and create the context with `powerPreference: "high-performance"`, `antialias: false`, `stencil: false`, `depth: false`. — [pmndrs/postprocessing](https://github.com/pmndrs/postprocessing)
- Tone mapping cost is "practically free." — [three.js forum](https://discourse.threejs.org/t/tone-mapping-overview/75204)
- Jimenez cites the frame budget as "16.6 ms for a 60 fps game." — [iryoku.com](https://www.iryoku.com/?p=1707)

### Inferences
- Pixel arithmetic (exact): 1080p = 2.07 MP; 1440p = 3.69 MP. Rendering at 2x DPR quadruples pixels (1440p display at DPR 1 → 5120x2880 = 14.7 MP). At RGBA8, one full-screen write at 2x-1440p is 59 MB; with several overlapping blended trays (each blended pixel = read + write), the current approach can move several hundred MB per frame, i.e., tens of GB/s at 60 fps. Integrated GPUs share system memory bandwidth with the CPU (theoretical figures for Iris Xe-class LPDDR4x/DDR4 laptops are commonly quoted in the ~50-68 GB/s range; not verified this session), so the current 2x supersample is likely the dominant cost and the source of fan noise/battery drain.
- Proposed pipeline budget at 1440p, 1x DPR: scene target R11F_G11F_B10F 14.7 MB per write; with ~2-3x average overdraw from trays, ~60-90 MB/frame of blend traffic; bloom ≈ 10 MB writes plus reads; final pass reads scene + bloom top mip and writes 14.7 MB RGBA8. Total ≈ 100-130 MB/frame ≈ 6-8 GB/s at a sustained 60 fps, well under the 2x-DPR status quo. At 1080p, multiply by 0.56.
- Render on demand: render only on input, animation, or resize (requestAnimationFrame loop that stops when idle); a static desktop UI then costs ~0 GPU when idle. With render-on-demand, keep grain/dither static so the image does not change between redraws.
- Cached layers: the bench changes rarely; render it once into a linear HDR texture and sample it (one fetch per pixel) rather than re-evaluating its material shader. Do the same per tray (render each tray into its own small HDR atlas tile when its content changes, then draw as a textured quad while dragging), turning drag frames into a few texture blits plus the post chain.
- Dynamic resolution while dragging: drop the scene pass to 0.67-0.75x during drag (viewport scale on the same FBO to avoid reallocations), upscale in the final pass (bilinear + CAS), and re-render at 1x on pointerup. Bloom already runs at ≤ half-res.
- Measurement: use EXT_disjoint_timer_query_webgl2 `TIME_ELAPSED_EXT` queries around each pass where available (check `GPU_DISJOINT_EXT` and discard disjoint results; results arrive asynchronously several frames later); fallback everywhere else: rAF delta and long-frame counting, plus an adaptive quality governor (drop bloom mip count, then scene scale) when frame time exceeds ~14 ms over a moving window.
- Avoid per-frame FBO/texture allocation and `readPixels`/`getError` calls in the hot path; they stall the GPU pipeline in ANGLE.

### Gaps
- No fetched benchmark gives measured ms per pass (scene, bloom, final) for WebGL2 on Intel Iris Xe at 1080p/1440p; budgets above are bandwidth arithmetic, not measurements. A 10-minute in-app timer-query capture on the user's own laptop (Chrome/Edge on Windows supports it) is the only reliable way to close this.
- Iris Xe memory bandwidth figure not verified this session.

## 8. WebGPU in 2026: browser support, whether it gives meaningful quality/performance gains here, and fallbacks

### Takeaway
WebGPU is now shipped in Chrome/Edge (Windows, macOS, ChromeOS; Linux only on Intel Gen12+ since 144), Firefox (Windows since 141, macOS since 145/147), and Safari 26 (macOS/iOS/iPadOS/visionOS). For this quad-based UI it offers no intrinsic image-quality gain over a correct WebGL2 HDR pipeline; the one real quality upgrade is HDR canvas output (`toneMapping: "extended"`, Chromium). Stay WebGL2-first, and add WebGPU later only as an optional HDR-display path.

### Cited Findings
- Chromium (Chrome/Edge): WebGPU shipped in 113 on Mac, Windows x86/x64, ChromeOS; Android 121 (Android 12+, ARM/Qualcomm/Intel); Linux Intel Gen12+ in 144, NVIDIA on Wayland in 147 (driver ≥ 535.183.01), other Linux GPUs behind a flag; Windows ARM64 behind a flag. — [gpuweb wiki: Implementation Status](https://github.com/gpuweb/gpuweb/wiki/implementation-status)
- Firefox: shipped on Windows in 141; macOS Apple Silicon in 145 on macOS 26+, and in 147 on all macOS versions; Intel Macs Nightly only; Linux Nightly only, with Mozilla expecting to ship on Linux in 2026; Android disabled by default. — [gpuweb wiki](https://github.com/gpuweb/gpuweb/wiki/implementation-status)
- Safari: enabled by default in macOS Tahoe 26, iOS 26, iPadOS 26, visionOS 26. — [gpuweb wiki](https://github.com/gpuweb/gpuweb/wiki/implementation-status)
- The gpuweb wiki page was last edited May 28, 2026, so Linux/Firefox status may have advanced since (flag as possibly stale). — [gpuweb wiki](https://github.com/gpuweb/gpuweb/wiki/implementation-status)
- WebGPU HDR canvas: `format: "rgba16float"`, `toneMapping: { mode: "extended" }` since Chrome 129. — [Chrome: What's New in WebGPU 129](https://developer.chrome.com/blog/new-in-webgpu-129)
- three.js WebGPURenderer can output 16 bits per channel as of r173. — [three.js forum](https://discourse.threejs.org/t/tone-mapping-overview/75204)
- Secondary/2026 commentary pages on WebGPU vs WebGL adoption exist but were not used as primary evidence. — [Cinevva: WebGPU vs WebGL for Games (2026)](https://app.cinevva.com/guides/webgpu-vs-webgl-games); [svilenkovic: WebGPU adoption 2026](https://svilenkovic.com/3d/webgpu-adoption-2026)

### Inferences
- Quality: everything in sections 1-6 (HDR targets, linear blending, Jimenez bloom, Neutral/AgX tone mapping, analytic AA, dithering, LUT grading, P3) is achievable in WebGL2 with identical visual results. WebGPU's quality-relevant extras are (a) HDR (above-SDR-white) canvas output in Chromium, and (b) a float canvas without the Chromium-only `drawingBufferStorage` path.
- Performance: the workload is fill/bandwidth-bound (a few full-screen passes plus blended quads), not CPU/draw-call bound, so WebGPU's lower driver overhead buys little. Compute shaders allow single-pass mip downsampling and shared-memory blurs, which can trim bloom cost somewhat on integrated GPUs, but bloom is already a small fraction of the frame in the proposed pipeline.
- Risk: Firefox on Linux and Intel Macs, and Chromium on pre-Gen12 Intel Linux, still lack WebGPU per the May 2026 status; a WebGL2 fallback would be mandatory anyway, so WebGPU means maintaining two backends. For a solo developer with bandwidth limits, that is a poor trade unless HDR-display output becomes a product goal.
- If adopted later: feature-detect with `navigator.gpu?.requestAdapter()`, check `adapter.info`/limits, keep shaders in a portable form (or use a library backend that targets both), and keep the WebGL2 pipeline as the default path. No extra downloads are required for either API beyond the app's own shader code.

### Gaps
- Firefox and Safari support for WebGPU `toneMapping: "extended"` HDR canvases was not confirmed.
- No measured WebGL2-vs-WebGPU comparison for a 2D compositing/post-processing workload on Intel Iris Xe was found.
- Status after May 28, 2026 (e.g., Firefox Linux shipping) not confirmed.
