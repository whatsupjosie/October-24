# Saving across PubCast, 2026-10-28, Claude

## Reason

Josie, 2026-10-28, asked for progress to be saveable everywhere:

- Foresight
- PubCast / Bella Faux Pas
- 2i: doc files, editing sessions and text sessions
- Bella Faux Pas and PubPartner: conversations, collaborations, new cartridges and avatars

This ledger is filled in step by step as each part lands.

## What already saved on the host before this work

These were found by reading the routes, and they are the stores this work builds on:

- **2i documents:** `PUT /api/writers-room/documents/{id}`, kept in sqlite with a revision per save and per owner.
- **Foresight workspace files:** `/api/foresight/workspace/file`.
- **PubPartner:** sessions and turns.
- **Conversations and messages:** the conversation archive, chat rooms and DMs.
- **Avatar library:** `/api/avatars/imports`.

These were browser-only:

- the Counter layout (`foresight.counter.v3:<owner>`)
- the studio's tuning

These were missing:

- studio progress
- cartridge creation
- avatar creation from PubPartner

## Step 1: 2i file workspace tests (commit 560b7d0)

`tests/test_foresight_file_workspace.py` was 13 failed against clean October-24. Its fixture did not mount the real routes the page calls. It now:

- mounts the real writers-room and auth routers
- uses a throwaway `users.db` with a real owner

The manuscript test now checks the real path: save to Reach, revision 1 and then revision 2, the owner in sqlite, and the text back after a reload. Result: 14 passed. The old file was preserved outside the repo before editing.

## Step 2: Bella Faux Pas progress on the host

| Path | Change |
| --- | --- |
| `modules/studio_progress.py` (new) | One record per owner in `data/studio_progress/<owner>.json`. Writes are validated, at most 256 KB, revisioned (`expected_revision` gives 409 on a stale writer), and written to a temp file and then `os.replace`d. |
| `main.py` | Mounts the router after the avatar library. |
| `static/world_walk_live.js` | `loadProgress`, `saveProgress` (debounced, skipped if unchanged), `flushProgress` (retries on failure, keepalive on page hide), `avatarLibrary`. Host detection is shared and cached. |
| `static/world_walk.html` | "Your saved avatars" picker from the library, with a link to the importer. A progress status line. It saves while you stand still, on page hide and every second if anything changed. On start it restores tuning, character, avatars and hologram. It restores room and spot too, unless the link names a place (`?view=` or `?live=`). |

Provenance: new code written for October-24, using its own avatar library (`modules/avatar_imports.py`) and auth (`modules/route_security.current_identity`). No donor repository was used.

Data: `data/studio_progress/` is runtime data under `data/`. The test writes only to a temp folder.

## Tested (observed, Linux, Python 3.12)

`tests/test_bella_faux_pas_progress.py`: 11 passed.

- **Store and routes:**
  - round trip
  - revisions
  - owner isolation
  - seven kinds of bad input refused with nothing written
  - oversize refused
  - a stale writer gets 409
- **Restart, the real program:**
  1. Start `run_reach.py` and create an owner.
  2. Import the Xbot mannequin into the library at its measured height.
  3. In a browser: go to the green room, walk to a spot, walk as RePete, pick the library avatar, tune the size to 1.25 and turn hologram on.
  4. Wait for the save, then quit PubCast and start it again on the same data folder.
  5. In a fresh browser, everything comes back: the room, the spot (within 0.02 px), RePete, the avatar actually loaded, hologram and the tuning.
  6. A link that names the dressing room still goes there, keeping your character.

Regression: the world, walker, host, launch, registry and file workspace tests all pass: 289 passed.

## Step 3: the Counter layout on the host

| Path | Change |
| --- | --- |
| `modules/counter_layout.py` (new) | `GET`/`PUT /api/foresight/counter-layout`: one version 3 layout per owner in `data/counter_layout/<owner>.json`, at most 2 MB and 64 trays, revisioned. It uses the same atomic store as step 2. |
| `modules/studio_progress.py` | The store takes a folder name and optional extra fields (`client_saved_at`). The studio's behaviour is unchanged. |
| `main.py` | Mounts it. |
| `static/foresight_counter.js` | New `opt.onSave(layout, keepalive)` hook, called with each saved layout. The page-hide flush passes `keepalive`. With no `onSave` it behaves exactly as before, and the browser copy and its error toast are unchanged. |
| `static/foresight_counter.html` | Mirrors each save to the host (debounced, retried, keepalive on page hide) and stamps the browser copy with its save time. On start it uses the newer of the browser copy and the host copy: a browser with no copy gets the host's, and a host that is older gets the browser's. `?nosave` and `?fresh` keep their meaning. |

Preserved before editing: `foresight_counter.js` and `foresight_counter.html` were copied outside the repo.

Tested: `tests/test_foresight_counter_layout_host.py`, 9 passed.

- **API:** round trip, owner isolation, six bad layouts refused, a stale writer gets 409, oversize gets 413.
- **The real Counter:**
  1. `run_reach.py`, sign in through `/login`, open 2i from File › Open….
  2. The open tray reaches the host on its own.
  3. Quit and restart PubCast.
  4. A fresh browser with no saved data signs in and gets the 2i tray back.
  5. A newer empty layout saved from elsewhere beats the first browser's older copy.

Regression: all 24 Foresight/Counter test files plus the studio tests, 148 passed. Still failing: the same 4 in `test_foresight_airgapped_ui.py`, which fail on clean October-24 with the same timeouts.

Found, not changed: a save made during a tray's 0.7 s opening animation records the tray as `closed`. The Counter saves again when the animation ends, so it matters only if the page dies inside that window. That is existing behaviour, and it was already true of the browser copy.

## Untested

- Windows / PowerShell 5.
- Two devices editing the same owner's progress or layout at once. The store refuses a stale writer only when it sends `expected_revision`; the walker sends none, so the last save wins.
